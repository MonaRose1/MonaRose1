# Cover letter template

Replace every `<...>` placeholder. Keep it under 300 words. The portfolio link does the selling; the letter's job is to make them open it.

---

Dear `<Hiring Manager name, or "Hiring Team">`,

I'm applying for the `<role title>` position. I'm a developer who writes documentation: I build software, then document it the way a docs team would, and my portfolio holds four samples written against code anyone can open and check.

Three things in the portfolio map to what you described in the posting:

- **Reference accuracy.** `<The posting asks for API documentation.>` I wrote a full reference for a FastAPI service from its route source: every endpoint, schema, status code and configuration variable, plus an error catalogue. It includes the behavior an integrator most needs to know and the docs usually omit.
- **Working with engineers.** My review of an existing README found 13 defects against the codebase, including a documented command that didn't exist, and delivered a replacement that fixed all of them. That is the loop I want to be in: read the code, find the gap between docs and behavior, fix it, ship it.
- **Sensitive domains.** `<The posting mentions AI, healthcare, finance or enterprise customers.>` I wrote model documentation for a computer-vision feature with explicit limitation and ethics sections, and data-handling and accessibility documentation for a hiring platform that processes candidate video.

I work in Markdown and Git, review documentation in pull requests, and check it in CI with Vale and a link checker. I'm comfortable reading the source to answer a question rather than guessing. `<Optional: one sentence about the company's product that shows you used it.>`

Portfolio: `<portfolio URL>`. The review with before/after is the fastest sample: `<link>`.

Thank you for your time.

`<Name>`
`<Email>` · `<Portfolio>` · `<GitHub>`

---

## Notes on using it

- **One specific sentence beats four general ones.** The `<company product>` line is the only place to show you looked at their product. Use it.
- **Match their vocabulary.** If the posting says "developer documentation" and "docs-as-code", use those words; if it says "content design", adapt without inventing experience.
- **Naming a tool they use is fine; claiming mastery is not.** "I write in Markdown and review in pull requests" is verifiable from the portfolio.
- **The review sample is the differentiator.** Most applicants send a tutorial. Send the thing that shows judgment under someone else's constraints.
