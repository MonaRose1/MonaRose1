# Resume material

Use these lines with the facts you can defend. Nothing here claims a job you have not done: the angle is *developer who documents*, which is a real and currently scarce profile.

## Positioning line

> **Technical Writer** · Developer documentation and API reference for AI and developer-tool products. I read the source, run the software, and write what it actually does.

## Summary block

> Full-stack developer (MERN, Python/FastAPI) moving into technical writing. I document the systems I build: API references from route source, product guides from real user journeys, and documentation reviews that find the claims a README gets wrong. Public portfolio of four documentation samples across developer tools, SaaS, AI/ML and regulated enterprise products, each with its working notes and a before/after review.

## Experience bullets

Pick four or five. Each one is written in the result-first shape recruiters scan for: what, how, impact.

- Wrote and published a four-part technical writing portfolio covering API reference, product documentation, AI/ML model documentation and enterprise compliance documentation, each grounded in a shipped codebase and published with the working process behind it.
- Audited an existing 253-line README against the codebase it documented; identified 13 defects including three that blocked new developers entirely, ranked them by reader impact, and delivered a replacement README that fixed all 13.
- Wrote a full API reference for a FastAPI service from its route source: 5 endpoints, request and response schemas, status codes, 14 configuration variables with defaults, and an error catalogue with cause and fix for every failure mode.
- Created onboarding and task documentation for an undocumented real-time multiplayer application, reducing the first-run path to five steps and documenting the six support issues that account for most failures.
- Documented an AI gaze-estimation feature as a model card with inputs, outputs, limitations, training-data gaps and ethical considerations, plus metric definitions precise enough to audit and the test-suite coverage boundary stated explicitly.
- Wrote enterprise-facing data-handling, security-and-access and accessibility documentation for a hiring platform handling candidate video and résumés, including a data inventory, a role-permission matrix and a WCAG 2.2 conformance statement with a dated issue list and remediation plan.
- Set up documentation as code: Markdown in Git, Vale style checking, markdownlint, link checking and a static site published from CI, with a project style guide defining voice, terminology and page types.
- Built a docs review practice: severity definitions tied to reader impact, evidence quoted with file references, and a stable numbering scheme so fixes can be tracked back to findings.

## How to describe this portfolio in an interview

Sixty seconds, in this order:

1. "I'm a developer who documents. Every sample in my portfolio is written against a repository I can open for you."
2. "Start with the review: I audited a README against its own `package.json` and found a documented command that doesn't exist."
3. "The API reference shows I can read route files and write accurate, copyable reference."
4. "The model card shows I can write about AI without overclaiming, which is where most AI docs fail."
5. "The enterprise set shows I can write the page a security reviewer accepts."

Then stop. Let them pick the follow-up.

## What not to claim

- Years of professional writing experience you do not have. Say "developer moving into documentation" and let the samples carry the weight.
- Clients or employers that did not hire you.
- Metrics from someone else's project.
- "Expert" in a tool you have used once. "Working knowledge" is credible; "expert" invites a test.
